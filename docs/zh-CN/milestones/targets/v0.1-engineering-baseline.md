# v0.1 Engineering Baseline

## 文档状态

本文是 Fluxcode `v0.1` 的里程碑工程基线目标，不是 `design/` 下的模块设计。它定义 `v0.1` 要真正跑通 `fluxcode run "实现一个贪吃蛇游戏"` 这类任务时必须具备的落地细节：AI Provider、配置文件、`AGENTS.md` loader、session management、tools、minimal MCP bridge、local skills、local commands、prompt 管理和 context 压缩。

英文对应文档：[`docs/en-US/milestones/targets/v0.1-engineering-baseline.md`](../../../en-US/milestones/targets/v0.1-engineering-baseline.md)。

## 1. 目标

`v0.1` 的工程目标是：在一个已有应用基础的本地仓库中，Fluxcode 能通过 CLI 调用真实模型，读取上下文，修改源码，运行已声明验证命令，并输出可审查 handoff。

这要求 `v0.1` 不只具备抽象 loop，还必须具备以下最小工程能力：

- 一个真实可用的 model provider adapter。
- 一个稳定的 `ModelClient` 内部协议，用于屏蔽不同模型厂商差异。
- 一个可解释、可覆盖、无 secrets 的 JSONC 配置文件。
- 一个最小 `AGENTS.md` loader，把仓库约束以 snapshot/hash 进入 context。
- 一个可 create / list / show / resume 的 local session management。
- 一组足以完成小型代码任务的基础 tools。
- 一个默认关闭或显式启用的 minimal MCP bridge。
- 一个只加载本地 instruction / workflow / command bundle 的 local skill loader。
- 一组 built-in / local command specs，统一 route 到 `TaskSpec`。
- 可版本化、可测试的 phase prompts。
- 不依赖完整 transcript 的 context budget / compaction 策略。

## Contract Lock Before Implementation

`v0.1` 实现必须先锁定 code-agent contract，再进入 provider adapter、tool 或 phase runner 编码。这个 contract 是实现验收口径，不表示当前 `src/` 已经具备这些能力。

必须先明确：

- `TaskRunState`：run id、task input、phase status、artifact refs、verification status、blocked reason、resume marker。
- `PendingInput` / `ResumeInput`：`waiting_permission` 使用 permission 输入与 `permissionId`；`blocked` 使用 question 输入与 `questionId`；CLI resume、`TaskRunState.resume`、event log 和 `AgentHandoff` 必须复用同一组 id。
- Session contract：stable session id、create / list / show / resume、cwd / repo root 固定、context snapshot、status transitions 和 resume semantics。
- `AgentHandoff`：final summary、changed files、verification、risks、blockers、required user decisions 和 trace / evidence refs。
- `AGENTS.md` contract：加载范围、snapshot/hash、冲突处理、缺失 / 不可读语义，以及进入 `ContextPack` 的位置。
- Provider contract：`ModelClient` request / response、tool-call turn、tool-result turn、provider error、missing credential fail-fast、fake / mock provider 测试路径。
- MCP contract：config-defined servers、list/call tools、disabled-by-default / explicit enabled、统一 permission / evidence / trace / session 绑定、不能绕过权限。
- Skill contract：local skill loader、instruction / workflow / command bundle、context / prompt registry 注入、禁止直接 side effect。
- Command contract：built-in / local command specs、command -> `TaskSpec` / phase event / session，禁止绕过 agent-loop / permission / session。
- Shell contract：allowlist、declared-command discovery、timeout、output cap、blocked / ask / deny 记录，以及测试命令 convention。
- Tool contract：read-only / mutating 分类、path boundary、read-before-write、stale write、edit match、permission decision。
- Artifact contract：`TaskSpec`、`ContextPack`、`ChangePlan`、`PatchSummary`、`VerificationResult`、`AgentHandoff` 的最小字段和 schema guard。
- Headless output envelope：`runId`、`status`、`pendingInput?`、`handoff?` 是 `--output json` 的最小机器可读字段；旧 `denied` 只能作为兼容状态映射到 canonical `blocked`。

Contract lock 的验收是 review-only：确认目标、非目标、schema、失败状态和测试约定。未完成前，不应直接实现真实 provider 或 mutating tool，以免把未确认的接口固化到代码里。

## Output and UI Boundary

本文重新建立 `v0.1` output / TUI decisions。`v0.1` 工程基线不交付正式 TUI / IDE cockpit，也不把 TUI 加入 release acceptance；release-critical path 仍是 headless JSON / text `AgentHandoff`。

CLI 输出边界：

- `--output json` 和 `--output text` 必须保留，并覆盖 non-TTY、CI、重定向、自动化调用和 crash fallback 场景。
- `--ui tui` 或独立 experimental command 只能是显式 opt-in；默认 `fluxcode run <task>` 不依赖 TUI。
- `AgentHandoff` schema 不因 UI 存在而变化；UI 只能展示 handoff、runtime events、`StepTrace` 和 permission prompt 状态。
- TUI 不驱动 permission、session、runtime mutation，也不能绕过 schema、permission、evidence、trace 或 handoff。
- runtime core 不 import `react`、`ink`、`@opentui/*`，主 runtime 不引入 Bun / Zig / native build chain。

如果后续引入 renderer，边界必须是：

```text
runtime event stream
  -> stable TuiViewModel
  -> InkRenderer | OpenTuiRenderer | PlainTextRenderer
```

`PlainTextRenderer` 是 non-TTY、CI、snapshot 和 crash fallback 的默认路径。Ink 只能作为后续 optional / lazy / experimental PoC；如果选定的 Ink 路径要求 Node `>=22`，必须设置 Node gate。`OpenTUI` 只作为 `v0.4+` adapter evaluation gate；只有当 `ActionGraph` 在 `v0.5+` 成为实际 UX surface 后，才考虑 cockpit hardening candidate。

## 2. AI Provider 方案

### 2.1 内部协议先行

Fluxcode 内部只依赖 `ModelClient`，不让业务 loop 直接依赖 OpenAI、Anthropic、Claude Code、MCP 或任意厂商协议。

```ts
type ModelTurn =
  | { type: "message"; content: string }
  | { type: "tool_calls"; content?: string; toolCalls: ToolCall[] };

interface ModelClient {
  generate(request: ModelRequest): Promise<ModelTurn>;
}
```

Provider adapter 的职责是把外部协议转换成这个 canonical form：

| 外部差异 | 内部归一 |
| --- | --- |
| OpenAI tool calls / Anthropic tool_use 命名不同 | 统一为 `ToolCall[]` |
| streaming / non-streaming 差异 | v0.1 先支持 non-streaming，streaming 后续只影响 UI |
| system / developer / user message 差异 | 统一为 `ModelMessage[]`，adapter 内部映射 |
| token 参数命名差异 | 统一为 `maxOutputTokens`、`temperature` |
| JSON mode / tool choice 支持差异 | v0.1 不依赖强 JSON mode，使用 prompt + schema repair 兜底 |

### 2.2 v0.1 Provider 优先级

| Priority | Provider | 用途 | 说明 |
| --- | --- | --- | --- |
| P0 | `fake` | 单元测试和集成测试 | 已存在，必须保留 |
| P0 | `openai-compatible` | 第一类真实模型适配 | 兼容 OpenAI、Azure OpenAI、兼容 OpenAI API 的本地或网关模型 |
| P1 | `anthropic-compatible` | Claude / Anthropic Messages API | 用于更贴近 Claude Code 的 tool_use 语义 |
| P2 | `custom-command` | 本地命令或企业内部模型代理 | 仅在有实际需求时实现 |

`v0.1` 不需要抽象成 LangChain / Vercel AI SDK 这类上层框架。优先保持 adapter 小而透明，便于调试 tool call 和权限问题。

### 2.3 Provider 失败语义

| 场景 | 处理 |
| --- | --- |
| 缺少 API key | 启动前失败，并提示缺少的 env 名称 |
| 429 / rate limit | 记录 provider error，可按配置有限重试 |
| tool call JSON 无法解析 | 进入一次 schema repair turn，仍失败则 block 当前 phase |
| 模型不支持 tools | 启动前或 phase 开始前失败，不降级为纯文本执行 |
| 输出超长 | 截断摘要并记录 truncation，不把长输出继续塞回 prompt |

## 3. Config 配置设计

### 3.1 配置文件定位

配置文件是 runtime policy，不是 secrets 存储。默认发现路径：

```text
~/.fluxcode/fluxcode.jsonc
~/.fluxcode/fluxcode.json
.fluxcode/fluxcode.jsonc
.fluxcode/fluxcode.json
```

规则：

- 同一层级内优先读取 `fluxcode.jsonc`，不存在时再读取 `fluxcode.json`。
- 全局配置和项目配置同时存在时都读取，并按 key 做 deep merge。
- 配置 merge 顺序为 default config -> global config -> project config -> CLI flags；项目配置覆盖全局配置。
- API key 只通过环境变量引用，例如 `apiKeyEnv`。
- 默认配置必须能跑 `fake` provider 测试。
- 真实 provider 必须显式设置为 default；全局配置不得存储 secret 本身。

## 4. Tools 最小集合

`v0.1` 的 tools 目标不是多，而是足以完成小型代码任务并具备安全边界。

| Tool | Priority | Mutating | 用途 | 当前状态 |
| --- | --- | --- | --- | --- |
| `list_directory` | P0 | no | 查看仓库结构 | 已有 |
| `read_file` | P0 | no | 读取源码、测试、配置 | 已有 |
| `search` | P0 | no | 搜索符号、文本和测试入口 | 已有 |
| `edit_file` | P0 | yes | 基于 old/new 或 range 的局部修改 | 已实装 P0：支持 exact replace / unique anchor insert，并经过 read-before-write、stale-write、edit-match gate |
| `write_file` | P0 | yes | 创建新文件或完整覆盖小文件 | 已收紧 P0：新文件需显式 `createIntent=true`；覆盖需本 run 读取且 hash 未变 |
| `shell_exec` | P0 | yes | 运行声明验证命令 | 已收紧 P0：仅允许 `tools.shell.allowCommands`、`package.json` scripts 或 permission ask/deny 路径 |
| `read_project_manifest` | P0 | no | 读取 package / tsconfig / test config 摘要 | 已实装 P0 summary：返回 config files 与 package scripts / declared commands |
| `git_diff` | P0 | no | 生成 changed files / diff summary，供 `AgentHandoff` 和安全回顾使用 | 已实装 P0 summary-only；仍不提供 git write automation 或完整 review workflow |
| `diagnostics` | P1 | no | LSP / TypeScript diagnostics | 后续实现 |

Minimal MCP bridge 不是普通 built-in tool 的替代品。它只能把 config-defined server tool 映射为 Fluxcode tool contract，并进入同一 permission、evidence、trace、session 管线；默认关闭或显式启用。不交付 marketplace、resource / prompt ecosystem 或 server management UI。

### 4.1 为什么需要 `edit_file`

只有 `write_file` 会把模型推向整文件重写，风险较高。`edit_file` 应支持最小局部修改：

```ts
type EditFileInput =
  | { path: string; mode: "replace"; oldText: string; newText: string; replaceAll?: boolean }
  | { path: string; mode: "insert_after" | "insert_before"; anchor: string; text: string };
```

约束：

- `oldText` 必须唯一匹配，除非 `replaceAll=true`。
- 修改前记录 file hash 或 mtime，用于 stale write 防护。
- 修改后返回 changed bytes、matched range 和 summary。

### 4.2 Shell 命令策略

`shell_exec` 不能是任意 shell。v0.1 只允许：

- 配置里 `tools.shell.allowCommands` 明确列出的命令。
- 从 project manifest 中声明的 scripts，例如 `npm test`、`npm run build`。
- 用户本轮明确确认的命令。

默认阻止：

- install：`npm install`、`pnpm add`、`pip install`。
- delete：`rm -rf`、批量删除。
- network：curl、wget、远程脚本。
- git write：commit、push、reset、checkout、rebase。

## 5. Prompt 管理

Prompt 不应散落在代码字符串里。v0.1 需要一个轻量 prompt registry。

推荐结构：

```text
src/prompts/
  system.ts
  phases/
    intake.ts
    understand.ts
    plan.ts
    edit.ts
    verify.ts
    handoff.ts
```

每个 prompt 定义：

```ts
type PromptTemplate = {
  id: string;
  version: string;
  phase: AgentPhase;
  render(input: PromptRenderInput): ModelMessage[];
  expectedOutput: string;
};
```

Prompt 管理规则：

- system prompt 只描述 agent 身份、工具边界、安全约束和 artifact 输出规则。
- phase prompt 描述当前阶段目标、允许工具、输出 schema 和失败处理。
- 不把大段历史 transcript 直接拼进 prompt；只传 `TaskSpec`、phase artifacts、recent steps 和必要 evidence summary。
- prompt id 和 version 写入 `StepTrace`，便于复现。
- 自定义 prompt 后续可支持，但 v0.1 不开放任意项目 prompt 覆盖安全规则。

## 6. Context 压缩

`v0.1` 不需要复杂 memory 系统，但必须避免 transcript 无限增长。

### 6.1 Context lanes

每次模型调用由四类上下文组成：

| Lane | 内容 | 是否可压缩 |
| --- | --- | --- |
| Task lane | `TaskSpec.objective`、acceptance、constraints、nonGoals | 不可丢失 |
| Artifact lane | `ContextPack`、`ChangePlan`、`PatchSummary`、`VerificationResult` | 可摘要但不能丢引用 |
| Evidence lane | 工具结果摘要、文件引用、命令输出摘要 | 可压缩 |
| Recent loop lane | 当前 phase 最近 N 步 ReAct 观察 | 可滑动窗口 |

### 6.2 压缩策略

当 prompt 超过 `context.maxPromptBytes` 时，按顺序处理：

1. 截断长工具输出，只保留 summary、references、truncated marker。
2. 压缩旧 `StepTrace` 为 phase summary。
3. 保留 changed files、verification failures、user constraints 和 open blockers。
4. 对已读文件内容只保留路径、原因和必要片段。
5. 如果仍超预算，block 当前 phase，要求缩小任务范围。

禁止压缩掉：

- 用户验收条件。
- 用户明确非目标。
- 权限拒绝或待确认项。
- 修改文件列表。
- 验证失败摘要。

## 7. 当前代码缺口

| 缺口 | 影响 | v0.1 处理 |
| --- | --- | --- |
| `openai-compatible` adapter 尚未实现 | CLI 默认只能 fake | 实现真实 provider adapter |
| `config-schema` 只校验顶层 | 配置错误发现晚 | 补充 runtime / prompts / context / shell allowlist 校验 |
| `edit_file` P0 已补齐 | 真实修改容易整文件覆盖 | 保持局部编辑工具走 read-before-write、stale-write、edit-match gate |
| `shell_exec` P0 已收紧 | 命令风险高 | 保持 declared command discovery、allowlist 与 dangerous command deny/ask |
| 轻量只读 `git_diff` P0 已补齐 | handoff 缺少 changed files / diff summary | 保持 summary-only `git_diff`；完整 diff review / review workflow 后置到 P1 |
| 缺少明确 `v0.1` code-agent contract | provider、tool、phase runner 容易各自定义接口 | 先完成 contract lock，再实现 adapter / tool / runner |
| session contract 过窄 | resume、permission 等状态难以恢复 | 增加 create / list / show / resume、status transitions、context snapshot |
| 缺少 `AGENTS.md` loader contract | 仓库约束可能变成未追踪 prompt 文本 | 增加 snapshot/hash 和 context binding |
| 缺少 minimal MCP bridge | 外部工具能力无法进入统一权限和证据管线 | 增加默认关闭 / 显式启用的 list/call tools bridge |
| 缺少 local skill loader | 本地工作流无法作为受控上下文能力复用 | 增加 local-only skill loader，禁止直接 side effects |
| 缺少 local command specs | 命令可能绕过 agent loop | 增加 command -> `TaskSpec` / phase event / session routing |
| prompt 硬编码在 `agent-loop.ts` | 难测试、难版本化 | 新增 prompt registry |
| context 依赖 transcript | 长任务不可控 | 新增 context builder / compactor |
| CLI 输出仍是 loop result | 缺少 handoff | 输出 `AgentHandoff` 和 artifact paths |
| 缺少 output / UI 边界 | TUI 可能误入 `v0.1` release-critical path | 保留 `--output json` / `--output text`，TUI 仅 opt-in 且不进入 runtime core |

### 7.1 Step 5 实现对齐状态

当前 `src/` 已补齐 `v0.1` Step 5 的最小实现切片：`AGENTS.md` 通过 repo root / cwd 边界读取并以 snapshot/hash/summary 进入 `ContextSnapshot`；local skills 只作为 instruction / workflow / command spec 注入 prompt/context；local commands 先转换为 `TaskSpec` 并写入 session event，再继续进入 phase runner；minimal MCP bridge 仅暴露显式 enabled server tools，并作为 Fluxcode `ToolRegistry` 工具经过 permission、evidence、trace 和 session 管线；phase prompt 通过轻量 prompt registry 渲染，context builder / compactor 在模型调用前保留 task、acceptance、constraints、changed files 和 verification lanes。

这只是 Step 5 的 adapter / prompt / context 接线状态，不表示 Step 6 的最终 release path、coverage gate、真实 provider smoke 或完整 handoff/recovery 验收已经完成。

### 7.2 Step 6 实现对齐状态

当前 `src/` 已补齐 Step 6 的 release-path 接线：`AgentHandoff` 在输出前补全 `changedFiles`、verification、risks、trace refs 与 evidence refs；`recovery_gate` 会修复可恢复的 blocked pending input，并在 failed / completed handoff 缺失或 pending tool state 悬挂时显式收敛为 failed handoff；CLI `run|resume|show|list` 继续输出 headless envelope，并按冻结 status / exit-code 表返回；`graph-ready` wrapper 只消费 headless contract，不反向定义 runtime 主线。

测试侧已加入 fake-model release-path fixture、resume negative/fallback fixture、coverage edge fixture，以及真实 provider 手动 smoke hook `npm run smoke:provider`。常规验收仍以 deterministic fake-model integration 为主；真实 provider smoke 需要先执行 `npm run build` 并提供 `FLUXCODE_MODEL_API_KEY`，可选提供 `FLUXCODE_MODEL_BASE_URL` / `FLUXCODE_MODEL_NAME`。

## 8. v0.1 实现顺序

1. Lock `v0.1` code-agent contract：`TaskRunState`、session lifecycle、`AGENTS.md` snapshot/hash、`AgentHandoff`、provider contract、MCP / skill / command contracts、shell allowlist / declared-command discovery、blocked / ask / deny 语义、test command convention。
2. 实现 provider / config gate，并新增 `openai-compatible` `ModelClient` adapter；真实 provider 必须显式配置并 fail fast。
3. 扩展 config：`runtime`、`prompts`、`agents`、`context`、`commands`、`skills`、`mcp`、`tools.shell.allowCommands`。
4. 新增 artifact schema guard：`TaskSpec`、`ContextPack`、`ChangePlan`、`PatchSummary`、`VerificationResult`、`AgentHandoff`。
5. 新增 session management：create / list / show / resume、status transitions、context snapshot、trace / evidence binding。
6. 新增 `AGENTS.md` loader，并把 snapshot/hash 写入 session context。
7. 新增 `edit_file`、`read_project_manifest`、轻量只读 `git_diff`，并收紧 `shell_exec`。
8. 新增 minimal MCP bridge、local skill loader、local command specs，全部 route through `TaskSpec -> Session -> PhaseRunner`。
9. 新增 prompt registry、phase prompts 和 context builder / compactor。
10. 新增 `PhaseRunner`，将现有 loop 收口到 `Intake -> Understand -> Plan -> Edit -> Verify -> Handoff`。
11. CLI `run` 输出 `AgentHandoff`，而不是只输出最终自然语言文本。
12. 锁定 output / UI boundary：non-TTY 和 CI 走 JSON / text 或 `PlainTextRenderer` fallback；experimental TUI 不改变默认 handoff。
13. 用 `FakeModelClient` / deterministic mock provider 覆盖 happy path、provider error、permission ask / deny、verification fail、context overflow、ambiguous scaffold / dependency blocking、session resume、AGENTS loading、MCP disabled / enabled、skill / command routing。

## 9. 验收

- 配置真实 provider 后，`fluxcode run "实现一个贪吃蛇游戏"` 不再返回 fake 默认消息。
- 对已有 Web / frontend 仓库，agent 能创建或修改源码文件。
- agent 能运行已声明测试或构建命令，并把结果写入 handoff。
- 无框架或缺少依赖决策时，agent 明确 block 并请求确认。
- prompt、context、tools、provider、permission 决策都能在 event log 或 step trace 中追溯。
- session lifecycle、`AGENTS.md` snapshot/hash、minimal MCP bridge、local skills 和 local commands 都进入同一 permission / evidence / trace / session 管线。
- `--output json` / `--output text` 保持可用；没有显式 opt-in 时，TUI 不影响 `AgentHandoff` 输出或 `v0.1` 验收。
