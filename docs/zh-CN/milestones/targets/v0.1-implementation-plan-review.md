# v0.1 Implementation Plan and Technical Review

## 文档状态

本文是 Fluxcode `v0.1` basic code agent 的实现计划与技术评审。它基于当前仓库代码、[`v0.1 Engineering Baseline`](./v0.1-engineering-baseline.md)、[`Code Agent Loop`](../../design/modules/code-agent-loop.md)，以及对 Claude Code、CodeWhale、Codex、opencode 的临时源码调研结论。

英文对应文档：[`docs/en-US/milestones/targets/v0.1-implementation-plan-review.md`](../../../en-US/milestones/targets/v0.1-implementation-plan-review.md)。

本文回答三个问题：

- 每个功能点采用什么方案。
- 是否引入依赖库，还是完全自研。
- 这个计划是否足以实现可运行的 `fluxcode run <task>`。

## 1. 总体选型结论

`v0.1` 采取“小依赖、强边界、可测试”的实现策略：

- Runtime 不引入 LangChain、Vercel AI SDK、Commander、Zod、tree-sitter、simple-git、execa 等新依赖。
- 使用 Node.js >= 20 的标准能力：`fetch`、`fs/promises`、`child_process`、`AbortController`、`crypto`。
- Provider、schema guard、edit tool、shell policy、prompt registry、context compaction 先自研最小版本。
- 只有在 v0.1 自研方案无法支撑安全或可维护性时，后续版本再引入依赖。

理由：当前 `package.json` 只有 TypeScript / Vitest 开发依赖。v0.1 的目标是先把本地 agent 闭环跑通，过早引入大型 agent framework 会放大调试面，并稀释 Fluxcode 自己的 runtime 边界。

## 2. 功能点方案选型矩阵

| 功能点 | 方案选型 | 新依赖 | 理由 | 评审结论 |
| --- | --- | --- | --- | --- |
| CLI entry | 保留现有手写 `parseArgs`，扩展 `run` 输出 `AgentHandoff` | 否 | 参数少，Commander 等依赖收益低 | 通过 |
| Session / TaskRun | 在现有 `SessionState` 旁新增 `TaskRunState` / `TaskRunStore`，文件系统 JSON 持久化 | 否 | 当前已有 session store，可复用模式 | 通过 |
| Model loop | 保留现有 `AgentLoop` 工具循环，新增 `PhaseRunner` 包装 phase-gated ReAct | 否 | 不破坏已有 ReAct 基础 | 通过 |
| Provider abstraction | 实现 `openai-compatible` adapter，使用 Node `fetch` | 否 | OpenAI-compatible 覆盖面够大，避免 SDK 差异 | 通过 |
| Tool contract | 扩展现有 `ToolDefinition`，保留轻量 schema | 否 | 当前已有 tool schema / registry | 通过 |
| Read/search | 先保留现有 `list_directory`、`read_file`、`search` | 否 | v0.1 足够；性能后续再优化 | 通过 |
| Edit/write | 新增 `edit_file`，严格 old/new 唯一匹配；限制 `write_file` 覆盖风险 | 否 | 生产 code agent 必须避免整文件重写 | 通过，必须优先实现 |
| Shell verify | 扩展 `shell_exec`：allowlist、manifest scripts、timeout、output cap | 否 | 不做任意 shell；不需 shell parser 依赖 | 通过 |
| Prompt registry | 新增 `src/prompts/` TypeScript prompt registry | 否 | prompt 需要版本化和测试，TS 文件即可 | 通过 |
| Context budget | 新增 context builder / compactor，按 lanes 手写压缩 | 否 | v0.1 不需要复杂 memory 框架 | 通过 |
| Evidence/event | 扩展现有 `EventLog` 和 `EvidenceStore`，新增 phase / step 事件 | 否 | 当前 append-only 机制已存在 | 通过 |
| Handoff | 新增 handoff builder，CLI 输出 handoff JSON | 否 | 简单结构化汇总 | 通过 |
| Recovery | event log + session snapshot + task run JSON 重建 | 否 | 完整 graph recovery 后置 | 通过 |
| Config schema | 扩展现有手写 validation | 否 | 配置结构有限，不引入 Ajv/Zod | 通过，但要补测试 |
| Tests | Vitest + temp filesystem fixtures + fake model scripts | 否 | 当前 declared test framework 是 Vitest | 通过 |

## 3. 分阶段实现计划

### Phase 0: 当前能力整理

目标：确认现有能力可复用，不做功能改造。

任务：

- 梳理 `src/core/agent-loop.ts` 的 tool call handling。
- 梳理 `src/tools/builtin.ts` 的 read / search / write / shell 行为。
- 梳理 `src/config/types.ts`、`src/config/defaults.ts` 和 `fluxcode.config.example.jsonc` 的缺口。
- 为现有 CLI / agent-loop 测试建立基线。

验收：

- 现有测试通过。
- 明确每个后续改造点对应文件。

### Phase 1: Provider and Config

目标：`fluxcode run` 能使用真实 provider，而不是默认 fake。

任务：

- 新增 `src/model/openai-compatible.ts`。
- 在 `createAgentLoop` 中根据 `config.models.default` 创建 provider。
- 扩展 config 类型：`runtime`、`prompts`、`context`、`tools.shell.allowCommands`。
- 支持 `${ENV_NAME}` placeholder resolve。
- 启动前执行 `provider_gate` 和 `config_gate`。

不引入依赖：

- 使用 Node `fetch` 调用 `/chat/completions` 或 OpenAI-compatible endpoint。
- 手写 request / response mapping。

验收：

- 缺少 API key 时 CLI fail fast，并指出 env 名称。
- fake provider 测试仍可运行。
- openai-compatible request mapping 有单元测试。

### Phase 2: PhaseRunner and Artifacts

目标：把现有 ReAct loop 收口为 phase-gated ReAct。

任务：

- 新增 `src/core/phases.ts`：`AgentPhase`、`PhaseContract`、默认 contracts。
- 新增 `src/core/run-state.ts`：`TaskRunState`、artifact apply、handoff builder。
- 在 `AgentLoop` 中引入 `runPhase`，复用现有 `handleToolCall` 逻辑。
- phase 完成时解析模型 message 中的 JSON artifact。
- schema 校验失败时执行一次 repair turn。

不引入依赖：

- 使用手写 type guard 校验 `TaskSpec`、`ContextPack`、`ChangePlan`、`PatchSummary`、`VerificationResult`、`AgentHandoff`。

验收：

- fake model happy path 能完整跑完 `Intake -> Understand -> Plan -> Edit -> Verify -> Handoff`。
- artifact 无效时进入 repair；repair 失败时 block。

### Phase 3: Tools and Gates

目标：支持真实代码修改和验证，同时具备 P0 gates。

任务：

- 新增 `edit_file`。
- 新增 `read_project_manifest`。
- 收紧 `write_file`：覆盖已有文件默认需要 read-before-write 或显式 create / overwrite intent。
- 收紧 `shell_exec`：只允许 allowlist、manifest scripts 或用户确认命令。
- 增加 path boundary、deny globs、stale write、edit match gate。

不引入依赖：

- `edit_file` 使用字符串唯一匹配。
- 文件 hash 使用 Node `crypto`。
- shell command 安全先采用 allowlist，不做 tree-sitter shell AST。

验收：

- 未读文件直接 edit 被拒绝。
- `oldText` 多匹配被拒绝。
- `.env`、`.git`、`node_modules` 路径被拒绝。
- `npm install`、`rm -rf`、`git push` 默认 blocked / ask。

### Phase 4: Prompt and Context

目标：prompt 可测试、可版本化，context 不依赖完整 transcript。

任务：

- 新增 `src/prompts/system.ts`。
- 新增 `src/prompts/phases/*.ts`。
- 新增 `src/context/build-context.ts`。
- 按 Task lane / Artifact lane / Evidence lane / Recent loop lane 构建 prompt。
- 超预算时压缩 tool output 和旧 steps。

不引入依赖：

- 手写 byte budget 和 truncation。
- 不引入 tokenizer。`v0.1` 用 bytes 近似，保守设置阈值。

验收：

- context overflow 时保留 acceptance、nonGoals、blockers、changed files、verification failures。
- prompt id / version 写入 `StepTrace`。

### Phase 5: Handoff, Recovery, Integration Tests

目标：形成可运行的 CLI 体验和集成测试闭环。

任务：

- CLI `run` 输出 `AgentHandoff`。
- `EventLog` 增加 phase / step 事件。
- `TaskRunStore` 支持 resume。
- 建立临时仓库 fixtures。
- 编写 snake game fixture 集成测试。

验收：

- `fluxcode run "实现一个贪吃蛇游戏"` 在已有 web app fixture 中产生代码变更和验证结果。
- interrupted tool call resume 不产生悬挂状态。
- failed verification 不被报告为 success。

## 4. 依赖评审

### 明确不引入的依赖

| 依赖类别 | 不引入原因 |
| --- | --- |
| LangChain / Vercel AI SDK | 抽象过宽，会隐藏 tool call / provider failure 细节 |
| Commander | CLI 当前参数简单，手写足够 |
| Zod / Ajv | v0.1 schema 数量有限，手写 guard 更直接 |
| execa | Node `child_process` 已够用，当前已有实现 |
| tree-sitter shell parser | v0.1 不做任意 shell，只跑 allowlist / manifest scripts |
| simple-git | v0.1 不做 commit / push / branch automation |
| diff / patch package | `edit_file` 严格 old/new 即可，复杂 patch 后置 |
| tokenizer | v0.1 用 byte budget 保守截断，后续按 provider 引入 tokenizer |

### 可后续评估的依赖

| 依赖类别 | 触发条件 |
| --- | --- |
| tokenizer | 真实 provider 上下文预算误差导致频繁失败 |
| shell parser | 需要支持更宽 shell 命令而不依赖 allowlist |
| patch / diff lib | 需要 multi-file hunk patch 和更好 diff render |
| LSP client | 需要 diagnostics 作为验证 gate |
| SQLite | JSON 文件式 session / evidence 恢复性能不足 |

## 5. 技术方案评审

### 优点

- 能复用现有代码，不推倒重来。
- 保留 ReAct 的可用性，同时增加 artifact boundary。
- 不引入大型框架，便于调试 provider、tool、permission 和 context 问题。
- 每个 P0 gate 都能写单元或集成测试。
- 后续能自然演进到 `ActionNode` / `ActionGraph`。

### 主要风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 模型不稳定输出 JSON artifact | phase 无法完成 | prompt schema + one repair turn + block handoff |
| OpenAI-compatible 供应商差异 | tool call mapping 出错 | adapter 单测 + provider capability flag |
| allowlist shell 太保守 | agent 无法验证部分项目 | handoff 中请求用户确认命令 |
| 不使用 tokenizer | context 预算不精确 | byte budget 保守阈值，真实 provider smoke test 调整 |
| `edit_file` 严格匹配导致失败 | 修改成功率下降 | 让模型 reread 文件并提供更多上下文，不启用 fuzzy 默认 |
| 无 OS sandbox | 安全边界有限 | 文档不声称 sandbox；用 permission/path/shell gates 控制 |

### 评审结论

该计划可以实现一个可运行的 `v0.1`，但必须接受三个边界：

- `v0.1` 是安全受限的本地 code agent，不是无界自动工程师。
- `v0.1` 的 shell 能力 intentionally conservative，验证命令必须来自 allowlist、manifest 或用户确认。
- `v0.1` 不声称具备完整 sandbox、graph runtime、MCP、IDE 或多 agent 能力。

在这些边界下，推荐进入实现阶段。

## 6. 测试计划

### 单元测试

| 模块 | 必测场景 |
| --- | --- |
| Config | default merge、project override、missing provider、invalid permission mode、env placeholder |
| Provider | fake script、openai-compatible tool call parse、missing API key、provider error |
| PhaseRunner | happy path、artifact invalid、repair success、repair failure、budget exhausted |
| Tools | read/search/write/edit shell schema、truncation、references |
| Gates | provider/config/task/context/tool_schema/permission/path/read_before_write/stale/edit/shell/verification/handoff/recovery |
| Prompt | prompt id/version、phase schema、safety constraints present |
| Context | compression keeps required lanes |
| Handoff | failed/skipped verification not success |

### 集成测试

| 测试 | Fixture | Fake model 脚本 | 断言 |
| --- | --- | --- | --- |
| basic edit | small TS package | read -> edit -> test -> handoff | 文件变更，测试通过 |
| snake game | Vite / vanilla app fixture | inspect -> create files -> build/test -> handoff | 游戏文件生成，验证通过 |
| permission ask | existing file edit | attempt write | 返回 waiting_permission，无写入 |
| verification fail | failing test fixture | edit -> test fail | handoff failed，含输出摘要 |
| context overflow | huge read output | read huge -> continue | tool output truncated，任务约束保留 |
| interrupted resume | stop after tool call | resume | 无悬挂 tool call，能安全继续或失败 |
| stale write | external file modify after read | edit old hash | stale gate 阻止 |

### 真实 Provider Smoke

真实 provider smoke 不进入默认 CI。手动命令示例：

```bash
FLUXCODE_MODEL_API_KEY=... fluxcode run "在这个 fixture 中实现一个贪吃蛇游戏并运行测试" --config fluxcode.config.jsonc
```

通过标准：

- 模型产生 tool calls。
- 发生真实文件修改。
- 运行声明验证命令。
- 输出 `AgentHandoff`。
- 不需要人工介入的 happy path 能完成；需要依赖安装或 scaffold 时明确 ask / block。
