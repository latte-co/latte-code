# v0.1 Implementation Plan and Technical Review

## 文档状态

本文是 Lattecode `v0.1` basic code agent 的实现计划与技术评审。它基于当前仓库代码、[`v0.1 Engineering Baseline`](./v0.1-engineering-baseline.md)、[`Code Agent Loop`](../../design/modules/code-agent-loop.md)，并参考 Claude Code、CodeWhale、Codex、opencode 的临时源码调研输入；相关执行决策已在本文重新建立。

英文对应文档：[`docs/en-US/milestones/targets/v0.1-implementation-plan-review.md`](../../../en-US/milestones/targets/v0.1-implementation-plan-review.md)。

本文回答三个问题：

- 每个功能点采用什么方案。
- 是否引入依赖库，还是完全自研。
- 这个计划是否足以实现可运行的 `lattecode run <task>`。

## Accepted Execution Alignment

本节把已采纳的执行口径重新建立为正式文档内容。工作计划和临时调研材料只能作为输入；正式依据以本文、[`v0.1 Engineering Baseline`](./v0.1-engineering-baseline.md)、[`Code Agent Loop`](../../design/modules/code-agent-loop.md) 以及维护中的 roadmap / task breakdown 为准。本文描述的是 `v0.1` 目标和计划，不表示 `src/` 已经实现完整能力。

### Thesis

Lattecode 先成为可信的 local-first code agent：能读取仓库、完成安全局部编辑、运行已声明验证命令，并输出可审查 handoff。Harness-native runtime 不从抽象 kernel 先行，而是从 working agent 的 `StepTrace`、`Evidence`、gate、handoff、effect record 和 verification record 中逐步长出来。

### Capability Priority

| Priority | Capability scope | `v0.1` execution meaning |
| --- | --- | --- |
| P0 | CLI、config、`AGENTS.md` loader、session management、agent-loop / phase runner、built-in tools（含最小 changed-files / diff summary）、minimal MCP bridge、local skills、local commands、permission、evidence / trace、`AgentHandoff` | 必须形成最小 contract-first code agent 闭环；缺失时不能宣称 `v0.1` runnable code agent 完成 |
| P1 | provider hardening、prompt registry、context lanes、更完整的 diff review / review workflow、external capability boundary hardening | 可以进入早期实现切片，但不得扩大成完整插件、IDE/TUI 或外部工具生态 |
| Deferred | full `ActionGraph` scheduler、multi-agent、plugin marketplace、MCP marketplace / resource / prompt ecosystem、skill hub、command marketplace、remote、strong sandbox claims | 不进入 `v0.1` 验收；相关表述必须明确为后续演进目标 |

### TUI Plan Alignment

本文重新建立 TUI / output decisions：`v0.1` 不引入正式 TUI / IDE cockpit，也不把 TUI 加入 release acceptance。`v0.1` 的输出验收仍以 headless JSON / text `AgentHandoff` 为准。

执行口径如下：

- `--output json` / `--output text` 必须保留，并服务于 non-TTY、CI、重定向和自动化调用。
- `--ui tui` 或独立 experimental command 只能作为 opt-in；不得改变默认 `lattecode run <task>` handoff 行为。
- TUI 只消费 runtime events、`StepTrace`、permission prompt 状态和最终 `AgentHandoff`；不得驱动 permission、session、runtime mutation。
- runtime core 不 import `react`、`ink`、`@opentui/*`，也不引入 Bun / Zig / native build chain。
- 后续 Ink PoC 必须走 optional / lazy / experimental boundary；如果选定的 Ink 路径要求 Node `>=22`，必须设置 Node gate。
- `OpenTUI` 只保留为 `v0.4+` adapter evaluation gate；不写成 `v0.4` 或 `v0.1` 必交付项。

### Contract-first Immediate Slice

立即实现切片必须先锁定 contract，再进入 provider / tool 编码：

1. Lock `v0.1` code-agent contract：CLI / config、`TaskRunState`、session lifecycle、`AGENTS.md` snapshot/hash、`AgentHandoff`、provider contract、minimal MCP / local skill / local command contracts、shell allowlist / declared-command discovery、blocked / ask / deny semantics、test command convention。
   - `TaskRunState.status` 的 canonical 集合固定为 `queued` / `running` / `waiting_permission` / `blocked` / `failed` / `completed`；旧 `denied` 只作为 legacy compatibility 状态，进入 headless envelope 或 `graph-ready` wrapper 时映射为 `blocked`。
   - `PendingInput` / `ResumeInput` 固定为 headless run / resume contract：permission 恢复使用 `permissionId`，question 恢复使用 `questionId`，并由 `TaskRunState.resume`、event log、`AgentHandoff.blockers` / `requiredDecisions` 共用。
   - `--output json` 的最小 headless envelope 固定为 `runId`、`status`、`pendingInput?`、`handoff?`；TUI / legacy loop output 不得重新定义该 contract。
2. Provider / config gate：真实 provider 必须显式配置并 fail fast；测试路径保留 deterministic fake / mock provider。
3. Artifact schemas：`TaskSpec`、`ContextPack`、`ChangePlan`、`PatchSummary`、`VerificationResult`、`PermissionDecision`、`StepTrace`、`AgentHandoff`。
4. Tools：built-in read/search/edit/write/shell/manifest/minimal diff summary；P0 `git_diff` 只用于 changed files / diff summary，不表示 `v0.1` 支持 git write automation；更完整的 diff review / review workflow 留到 P1。
5. Minimal MCP / skill / command：MCP 只支持 config-defined servers 的 list/call tools，默认 disabled 或 explicit enabled；skill 只加载本地 instruction / workflow / command bundle；command specs 只能 route through `TaskSpec` / phase / session。
6. Phase runner：在现有 ReAct loop 外收口 `Intake -> Understand -> Plan -> Edit -> Verify -> Handoff`，并保证主链路为 `CLI / local command / local skill / minimal MCP bridge / built-in tools -> TaskSpec -> Session / TaskRunState -> ContextPack -> AgentLoop / PhaseRunner -> PermissionDecision -> Evidence / StepTrace -> AgentHandoff`。
7. Fixture tests：用 fake / mock model 覆盖 read-plan-edit-verify-handoff、permission ask/deny、verification failure、context overflow、ambiguous scaffold / dependency blocking、session resume、AGENTS loading、MCP disabled / enabled、skill / command routing。

## 1. 总体选型结论

`v0.1` 采取“小依赖、强边界、可测试”的实现策略：

- Runtime 不引入 LangChain、Vercel AI SDK、Commander、Zod、tree-sitter、simple-git、execa 等新依赖。
- 使用 Node.js >= 20 的标准能力：`fetch`、`fs/promises`、`child_process`、`AbortController`、`crypto`。
- Provider、schema guard、edit tool、shell policy、prompt registry、context compaction 先自研最小版本。
- 只有在 v0.1 自研方案无法支撑安全或可维护性时，后续版本再引入依赖。

理由：当前 `package.json` 只有 TypeScript / Vitest 开发依赖。v0.1 的目标是先把本地 agent 闭环跑通，过早引入大型 agent framework 会放大调试面，并稀释 Lattecode 自己的 runtime 边界。

## 3. 分阶段实现计划

### Phase 0: Contract Lock and 当前能力整理

目标：先锁定 `v0.1` code-agent contract，再确认现有能力可复用；contract 接受前不直接开写 provider 或 mutating tool。

任务：

- 固化 `TaskRunState`、`AgentHandoff`、provider contract 和 phase artifact schema 名称。
- 固化 session lifecycle、`AGENTS.md` snapshot/hash、minimal MCP bridge、local skill loader、local command specs 的 contract。
- 固化 shell allowlist / declared-command discovery、blocked / ask / deny 语义和 test command convention。
- 梳理 `src/core/agent-loop.ts` 的 tool call handling。
- 梳理 `src/tools/builtin.ts` 的 read / search / write / shell 行为。
- 梳理 `src/config/types.ts`、`src/config/defaults.ts` 和 `lattecode.config.example.jsonc` 的缺口。
- 为现有 CLI / agent-loop 测试建立基线。

验收：

- contract 清单被本文和 engineering baseline 共同确认。
- 现有测试通过。
- 明确每个后续改造点对应文件。

### Phase 1: Provider and Config

目标：`lattecode run` 能使用真实 provider，而不是默认 fake。

任务：

- 新增 `src/model/openai-compatible.ts`。
- 在 `createAgentLoop` 中根据 `config.models.default` 创建 provider。
- 扩展 config 类型：`runtime`、`prompts`、`agents`、`context`、`commands`、`skills`、`mcp`、`tools.shell.allowCommands`。
- 支持 `${ENV_NAME}` placeholder resolve。
- 启动前执行 `provider_gate` 和 `config_gate`。

不引入依赖：

- 使用 Node `fetch` 调用 `/chat/completions` 或 OpenAI-compatible endpoint。
- 手写 request / response mapping。

验收：

- 缺少 API key 时 CLI fail fast，并指出 env 名称。
- fake provider 测试仍可运行。
- openai-compatible request mapping 有单元测试。

### Phase 2: PhaseRunner and Artifacts

目标：把现有 ReAct loop 收口为 phase-gated ReAct。

任务：

- 新增 `src/core/phases.ts`：`AgentPhase`、`PhaseContract`、默认 contracts。
- 新增 `src/core/run-state.ts`：`TaskRunState`、artifact apply、handoff builder。
- 新增或扩展 `TaskRunStore`：create / list / show / resume、status transitions、context snapshot。
- 在 `AgentLoop` 中引入 `runPhase`，复用现有 `handleToolCall` 逻辑。
- phase 完成时解析模型 message 中的 JSON artifact。
- schema 校验失败时执行一次 repair turn。

不引入依赖：

- 使用手写 type guard 校验 `TaskSpec`、`ContextPack`、`ChangePlan`、`PatchSummary`、`VerificationResult`、`AgentHandoff`。

验收：

- fake model happy path 能完整跑完 `Intake -> Understand -> Plan -> Edit -> Verify -> Handoff`。
- artifact 无效时进入 repair；repair 失败时 block。

实现切片状态（2026-06-07）：`TaskRunState`、`TaskSpec`、`ContextPack`、`ChangePlan`、`PatchSummary`、`VerificationResult`、`StepTrace`、`AgentHandoff` 的最小 schema / type guard、phase-gated runner、artifact repair、pending permission / question resume 状态转换，以及 session / event / evidence 绑定已经作为 Step 3 范围落地。随后 Step 2b 已把 CLI headless contract 接到 `run|resume|show|list`、`--output json|text`、`resume --input '<ResumeInput JSON>'`、canonical envelope 与 status / exit-code 映射；P0 `edit_file` / manifest / diff 工具、MCP / skill / command routing 和 release coverage gate 仍属于后续 Step 4-6，不因本切片而视为完成。

### Phase 3: Tools and Gates

目标：支持真实代码修改和验证，同时具备 P0 gates。

任务：

- 新增 `edit_file`。
- 新增 `read_project_manifest`。
- 新增轻量只读 `git_diff`，用于 changed files / diff summary。
- 新增 minimal MCP bridge：config-defined servers、list/call tools、disabled-by-default / explicit enabled、统一 permission / evidence / trace / session。
- 收紧 `write_file`：覆盖已有文件默认需要 read-before-write 或显式 create / overwrite intent。
- 收紧 `shell_exec`：只允许 allowlist、manifest scripts 或用户确认命令。
- 增加 path boundary、deny globs、stale write、edit match gate。

不引入依赖：

- `edit_file` 使用字符串唯一匹配。
- 文件 hash 使用 Node `crypto`。
- shell command 安全先采用 allowlist，不做 tree-sitter shell AST。

验收：

- 未读文件直接 edit 被拒绝。
- `oldText` 多匹配被拒绝。
- `.env`、`.git`、`node_modules` 路径被拒绝。
- `npm install`、`rm -rf`、`git push` 默认 blocked / ask。

### Phase 4: Prompt and Context

目标：prompt 可测试、可版本化，context 不依赖完整 transcript。

任务：

- 新增 `src/prompts/system.ts`。
- 新增 `src/prompts/phases/*.ts`。
- 新增 `src/context/build-context.ts`。
- 新增 `AGENTS.md` loader，并把 snapshot/hash、pinned constraints 写入 context snapshot。
- 新增 local skill loader：只加载本地 instruction / workflow / command bundle，不能直接执行 side effects。
- 新增 local command specs：command -> `TaskSpec` / phase event / session。
- 按 Task lane / Artifact lane / Evidence lane / Recent loop lane 构建 prompt。
- 超预算时压缩 tool output 和旧 steps。

不引入依赖：

- 手写 byte budget 和 truncation。
- 不引入 tokenizer。`v0.1` 用 bytes 近似，保守设置阈值。

验收：

- context overflow 时保留 acceptance、nonGoals、blockers、changed files、verification failures。
- prompt id / version 写入 `StepTrace`。

### Phase 5: Handoff, Recovery, Integration Tests

目标：形成可运行的 CLI 体验和集成测试闭环。

任务：

- CLI `run` 输出 `AgentHandoff`。
- `EventLog` 增加 phase / step 事件。
- `TaskRunStore` 支持 resume。
- session resume 覆盖 `waiting_permission`、`blocked`、`failed`、`completed` 四类语义。
- 建立临时仓库 fixtures。
- 编写 snake game fixture 集成测试。

验收：

- `lattecode run "实现一个贪吃蛇游戏"` 在已有 web app fixture 中产生代码变更和验证结果。
- interrupted tool call resume 不产生悬挂状态。
- failed verification 不被报告为 success。

## 4. 依赖评审

### 明确不引入的依赖

| 依赖类别 | 不引入原因 |
| --- | --- |
| LangChain / Vercel AI SDK | 抽象过宽，会隐藏 tool call / provider failure 细节 |
| Commander | CLI 当前参数简单，手写足够 |
| Zod / Ajv | v0.1 schema 数量有限，手写 guard 更直接 |
| execa | Node `child_process` 已够用，当前已有实现 |
| tree-sitter shell parser | v0.1 不做任意 shell，只跑 allowlist / manifest scripts |
| simple-git | v0.1 不做 commit / push / branch automation |
| diff / patch package | `edit_file` 严格 old/new 即可，复杂 patch 后置 |
| tokenizer | v0.1 用 byte budget 保守截断，后续按 provider 引入 tokenizer |
| `react` / `ink` / `@opentui/*` | `v0.1` 不交付正式 TUI；UI dependency 不能进入 runtime core 或 release-critical path |

### 可后续评估的依赖

| 依赖类别 | 触发条件 |
| --- | --- |
| tokenizer | 真实 provider 上下文预算误差导致频繁失败 |
| shell parser | 需要支持更宽 shell 命令而不依赖 allowlist |
| patch / diff lib | 需要 multi-file hunk patch 和更好 diff render |
| LSP client | 需要 diagnostics 作为验证 gate |
| SQLite | JSON 文件式 session / evidence 恢复性能不足 |
| Ink experimental package | 只有在 `AgentHandoff`、runtime events 和 `TuiViewModel` 边界稳定后评估；若选定路径要求 Node `>=22`，必须 Node gate |

## 5. 技术方案评审

### 优点

- 能复用现有代码，不推倒重来。
- 保留 ReAct 的可用性，同时增加 artifact boundary。
- 不引入大型框架，便于调试 provider、tool、permission 和 context 问题。
- 每个 P0 gate 都能写单元或集成测试。
- 后续能自然演进到 `ActionNode` / `ActionGraph`。

### 主要风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 模型不稳定输出 JSON artifact | phase 无法完成 | prompt schema + one repair turn + block handoff |
| OpenAI-compatible 供应商差异 | tool call mapping 出错 | adapter 单测 + provider capability flag |
| allowlist shell 太保守 | agent 无法验证部分项目 | handoff 中请求用户确认命令 |
| 不使用 tokenizer | context 预算不精确 | byte budget 保守阈值，真实 provider smoke test 调整 |
| `edit_file` 严格匹配导致失败 | 修改成功率下降 | 让模型 reread 文件并提供更多上下文，不启用 fuzzy 默认 |
| 无 OS sandbox | 安全边界有限 | 文档不声称 sandbox；用 permission/path/shell gates 控制 |

### 评审结论

该计划可以实现一个可运行的 `v0.1`，但必须接受三个边界：

- `v0.1` 是安全受限的本地 code agent，不是无界自动工程师。
- `v0.1` 的 shell 能力 intentionally conservative，验证命令必须来自 allowlist、manifest 或用户确认。
- `v0.1` 交付 minimal MCP bridge，但不声称具备完整 MCP platform、marketplace、resource / prompt ecosystem、skill hub、command marketplace、完整 sandbox、graph runtime、IDE 或多 agent 能力。

在这些边界下，推荐进入实现阶段。

### 真实 Provider Smoke

真实 provider smoke 不进入默认 CI。手动命令示例：

```bash
LATTECODE_MODEL_API_KEY=... lattecode run "在这个 fixture 中实现一个贪吃蛇游戏并运行测试" --config lattecode.config.jsonc
# 或在已构建 CLI 后运行最小 smoke hook：
LATTECODE_MODEL_API_KEY=... npm run smoke:provider
```

通过标准：

- 模型产生 tool calls。
- 发生真实文件修改。
- 运行声明验证命令。
- 输出 `AgentHandoff`。
- 不需要人工介入的 happy path 能完成；需要依赖安装或 scaffold 时明确 ask / block。
