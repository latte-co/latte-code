# v0.1 Implementation Plan and Technical Review

## Status

This document is the implementation plan and technical review for Fluxcode `v0.1` basic code agent. It is based on the current repository, [`v0.1 Engineering Baseline`](./v0.1-engineering-baseline.md), [`Code Agent Loop`](../../design/modules/code-agent-loop.md), and temporary source research of Claude Code, CodeWhale, Codex, and opencode.

Chinese counterpart: [`docs/zh-CN/milestones/targets/v0.1-implementation-plan-review.md`](../../../zh-CN/milestones/targets/v0.1-implementation-plan-review.md).

This document answers:

- Which solution each feature uses.
- Whether it introduces dependencies or is implemented in-house.
- Whether the plan is enough to implement runnable `fluxcode run <task>`.

## 1. Overall Choice

`v0.1` follows a small-dependency, strong-boundary, testable implementation strategy:

- Do not add LangChain, Vercel AI SDK, Commander, Zod, tree-sitter, simple-git, or execa as runtime dependencies.
- Use Node.js >= 20 standard capabilities: `fetch`, `fs/promises`, `child_process`, `AbortController`, `crypto`.
- Implement minimal provider, schema guards, edit tool, shell policy, prompt registry, and context compaction in-house first.
- Introduce dependencies later only when the in-house `v0.1` implementation cannot support safety or maintainability.

Reason: current `package.json` only has TypeScript / Vitest dev dependencies. `v0.1` should first make the local agent loop work. Large agent frameworks would expand the debug surface and weaken Fluxcode's own runtime boundaries.

## 2. Feature Choice Matrix

| Feature | Choice | New dependency | Reason | Review |
| --- | --- | --- | --- | --- |
| CLI entry | Keep hand-written `parseArgs`; extend `run` to output `AgentHandoff` | No | Few args; Commander adds little | Pass |
| Session / TaskRun | Add `TaskRunState` / `TaskRunStore` next to current `SessionState`, persisted as filesystem JSON | No | Existing session store pattern is enough | Pass |
| Model loop | Keep existing `AgentLoop`; add `PhaseRunner` around phase-gated ReAct | No | Preserves existing ReAct foundation | Pass |
| Provider abstraction | Implement `openai-compatible` adapter using Node `fetch` | No | OpenAI-compatible covers broad providers and avoids SDK variance | Pass |
| Tool contract | Extend current `ToolDefinition`; keep lightweight schema | No | Tool schema / registry already exist | Pass |
| Read/search | Keep current `list_directory`, `read_file`, `search` | No | Enough for `v0.1`; optimize later | Pass |
| Edit/write | Add strict old/new `edit_file`; constrain `write_file` overwrites | No | Production code agents need scoped edits | Pass, high priority |
| Shell verify | Extend `shell_exec` with allowlist, manifest scripts, timeout, output cap | No | Do not run arbitrary shell; no shell parser needed | Pass |
| Prompt registry | Add TypeScript prompt registry under `src/prompts/` | No | Prompts need versioning and tests | Pass |
| Context budget | Add context builder / compactor using lanes | No | No complex memory framework needed | Pass |
| Evidence/event | Extend current `EventLog` and `EvidenceStore` with phase / step events | No | Append-only mechanism already exists | Pass |
| Handoff | Add handoff builder and CLI JSON output | No | Simple structured summary | Pass |
| Recovery | Rebuild from event log + session snapshot + task run JSON | No | Full graph recovery deferred | Pass |
| Config schema | Extend current hand-written validation | No | Config is limited; Ajv/Zod unnecessary | Pass, add tests |
| Tests | Vitest + temp filesystem fixtures + fake model scripts | No | Vitest is the declared framework | Pass |

## 3. Phased Implementation Plan

### Phase 0: Current Capability Baseline

Goal: confirm what can be reused before changing behavior.

Tasks:

- Review `src/core/agent-loop.ts` tool call handling.
- Review `src/tools/builtin.ts` read / search / write / shell behavior.
- Review gaps in `src/config/types.ts`, `src/config/defaults.ts`, and `fluxcode.config.example.jsonc`.
- Establish tests as current baseline.

Acceptance:

- Existing tests pass.
- Every later change has an owning file.

### Phase 1: Provider and Config

Goal: `fluxcode run` can use a real provider instead of fake default.

Tasks:

- Add `src/model/openai-compatible.ts`.
- Create provider from `config.models.default` in `createAgentLoop`.
- Extend config types with `runtime`, `prompts`, `context`, `tools.shell.allowCommands`.
- Resolve `${ENV_NAME}` placeholders.
- Run `provider_gate` and `config_gate` before starting.

No new dependency:

- Use Node `fetch` for `/chat/completions` or OpenAI-compatible endpoint.
- Hand-write request / response mapping.

Acceptance:

- Missing API key fails fast and names the env var.
- Fake provider tests still run.
- OpenAI-compatible request mapping has unit tests.

### Phase 2: PhaseRunner and Artifacts

Goal: close existing ReAct loop with phase artifacts.

Tasks:

- Add `src/core/phases.ts`: `AgentPhase`, `PhaseContract`, default contracts.
- Add `src/core/run-state.ts`: `TaskRunState`, artifact apply, handoff builder.
- Introduce `runPhase` in `AgentLoop`, reusing current `handleToolCall` logic.
- Parse JSON artifact from model message on phase completion.
- Allow one repair turn when schema validation fails.

No new dependency:

- Use hand-written type guards for `TaskSpec`, `ContextPack`, `ChangePlan`, `PatchSummary`, `VerificationResult`, `AgentHandoff`.

Acceptance:

- Fake model happy path runs `Intake -> Understand -> Plan -> Edit -> Verify -> Handoff`.
- Invalid artifact enters repair; repair failure blocks.

### Phase 3: Tools and Gates

Goal: support real code changes and verification with P0 gates.

Tasks:

- Add `edit_file`.
- Add `read_project_manifest`.
- Tighten `write_file`: overwriting existing files requires read-before-write or explicit create / overwrite intent.
- Tighten `shell_exec`: only allow allowlist, manifest scripts, or user-confirmed commands.
- Add path boundary, deny globs, stale write, edit match gates.

No new dependency:

- `edit_file` uses exact unique string matching.
- File hash uses Node `crypto`.
- Shell safety uses allowlist first; no tree-sitter shell AST.

Acceptance:

- Direct edit without prior read is rejected.
- Multiple `oldText` matches are rejected.
- `.env`, `.git`, `node_modules` paths are blocked.
- `npm install`, `rm -rf`, `git push` default to blocked / ask.

### Phase 4: Prompt and Context

Goal: prompts are testable and versioned; context does not depend on full transcript.

Tasks:

- Add `src/prompts/system.ts`.
- Add `src/prompts/phases/*.ts`.
- Add `src/context/build-context.ts`.
- Build prompt from Task lane / Artifact lane / Evidence lane / Recent loop lane.
- Compress tool output and old steps when over budget.

No new dependency:

- Hand-write byte budget and truncation.
- Do not add tokenizer in `v0.1`; use conservative byte threshold.

Acceptance:

- Context overflow preserves acceptance, nonGoals, blockers, changed files, verification failures.
- Prompt id / version is written into `StepTrace`.

### Phase 5: Handoff, Recovery, Integration Tests

Goal: runnable CLI experience and integration test loop.

Tasks:

- CLI `run` outputs `AgentHandoff`.
- `EventLog` adds phase / step events.
- `TaskRunStore` supports resume.
- Add temporary repository fixtures.
- Add snake game fixture integration test.

Acceptance:

- `fluxcode run "implement a snake game"` in an existing web app fixture produces code changes and verification results.
- Interrupted tool call resume does not leave dangling state.
- Failed verification is not reported as success.

## 4. Dependency Review

### Dependencies Explicitly Not Added

| Dependency category | Reason |
| --- | --- |
| LangChain / Vercel AI SDK | Too broad; hides tool call / provider failure details |
| Commander | CLI args are simple enough |
| Zod / Ajv | Few schemas in `v0.1`; hand-written guards are clearer |
| execa | Node `child_process` is enough; current implementation already uses it |
| tree-sitter shell parser | `v0.1` does not run arbitrary shell; only allowlist / manifest scripts |
| simple-git | No commit / push / branch automation in `v0.1` |
| diff / patch package | Strict old/new `edit_file` is enough; complex patch later |
| tokenizer | `v0.1` uses conservative byte budget; tokenizer can be provider-specific later |

### Dependencies to Reconsider Later

| Dependency category | Trigger |
| --- | --- |
| tokenizer | Provider context budget errors are frequent |
| shell parser | Need broader shell support beyond allowlist |
| patch / diff library | Need multi-file hunk patch and better diff render |
| LSP client | Need diagnostics as verification gate |
| SQLite | JSON session / evidence recovery becomes too slow |

## 5. Technical Review

### Strengths

- Reuses existing code; no rewrite.
- Keeps ReAct usability while adding artifact boundaries.
- Avoids large frameworks, improving debuggability for provider, tool, permission, and context failures.
- Every P0 gate can be covered by unit or integration tests.
- Evolves naturally toward `ActionNode` / `ActionGraph`.

### Main Risks

| Risk | Impact | Mitigation |
| --- | --- | --- |
| Model outputs unstable JSON artifacts | Phase cannot complete | Prompt schema + one repair turn + blocked handoff |
| OpenAI-compatible provider differences | Tool call mapping fails | Adapter unit tests + provider capability flags |
| Shell allowlist too conservative | Some projects cannot verify | Ask user and record skipped / blocked verification |
| No tokenizer | Context budget imprecise | Conservative byte budget and real provider smoke tuning |
| Strict `edit_file` failures | Lower edit success | Reread file and ask for more context; no fuzzy default |
| No OS sandbox | Safety boundary limited | Do not claim sandbox; rely on permission/path/shell gates |

### Review Conclusion

The plan can implement a runnable `v0.1`, with three explicit boundaries:

- `v0.1` is a safety-constrained local code agent, not an unbounded autonomous engineer.
- `v0.1` shell is intentionally conservative; verification commands must come from allowlist, manifest, or user confirmation.
- `v0.1` does not claim full sandbox, graph runtime, MCP, IDE, or multi-agent capabilities.

Within those boundaries, proceed to implementation.

## 6. Test Plan

### Unit Tests

| Module | Required cases |
| --- | --- |
| Config | default merge, project override, missing provider, invalid permission mode, env placeholder |
| Provider | fake script, openai-compatible tool call parse, missing API key, provider error |
| PhaseRunner | happy path, invalid artifact, repair success, repair failure, budget exhausted |
| Tools | read/search/write/edit/shell schema, truncation, references |
| Gates | provider/config/task/context/tool_schema/permission/path/read_before_write/stale/edit/shell/verification/handoff/recovery |
| Prompt | prompt id/version, phase schema, safety constraints present |
| Context | compression preserves required lanes |
| Handoff | failed/skipped verification is not success |

### Integration Tests

| Test | Fixture | Fake model script | Assertions |
| --- | --- | --- | --- |
| basic edit | small TS package | read -> edit -> test -> handoff | file changed, tests pass |
| snake game | Vite / vanilla app fixture | inspect -> create files -> build/test -> handoff | game files generated, verification passes |
| permission ask | existing file edit | attempt write | returns waiting_permission, no write |
| verification fail | failing test fixture | edit -> test fail | handoff failed with output summary |
| context overflow | huge read output | read huge -> continue | output truncated, task constraints retained |
| interrupted resume | stop after tool call | resume | no dangling tool call; continue or fail safely |
| stale write | external file modify after read | edit old hash | stale gate blocks |

### Real Provider Smoke

Real provider smoke is not part of default CI. Example manual command:

```bash
FLUXCODE_MODEL_API_KEY=... fluxcode run "implement a snake game in this fixture and run tests" --config fluxcode.config.jsonc
```

Pass criteria:

- Model produces tool calls.
- Real files are changed.
- Declared verification command runs.
- `AgentHandoff` is emitted.
- Happy path completes without human intervention; dependency install or scaffold needs ask / block.
