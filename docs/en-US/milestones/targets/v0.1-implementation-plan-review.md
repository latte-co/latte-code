# v0.1 Implementation Plan and Technical Review

## Status

This document is the implementation plan and technical review for Fluxcode `v0.1` basic code agent. It is based on the current repository, [`v0.1 Engineering Baseline`](./v0.1-engineering-baseline.md), [`Code Agent Loop`](../../design/modules/code-agent-loop.md), and temporary source-research input from Claude Code, CodeWhale, Codex, and opencode; the accepted execution decisions are re-established in this document.

Chinese counterpart: [`docs/zh-CN/milestones/targets/v0.1-implementation-plan-review.md`](../../../zh-CN/milestones/targets/v0.1-implementation-plan-review.md).

This document answers:

- Which solution each feature uses.
- Whether it introduces dependencies or is implemented in-house.
- Whether the plan is enough to implement runnable `fluxcode run <task>`.

## Accepted Execution Alignment

This section re-establishes the accepted execution alignment as maintained documentation. Working plans and temporary research material are inputs only; the formal basis is this document, [`v0.1 Engineering Baseline`](./v0.1-engineering-baseline.md), [`Code Agent Loop`](../../design/modules/code-agent-loop.md), and the maintained roadmap / task breakdown. This document describes `v0.1` targets and plans; it does not mean `src/` already implements the full capability set.

### Thesis

Fluxcode should first become a trusted local-first code agent: it can read a repository, make safe scoped edits, run declared verification commands, and produce reviewable handoff. The harness-native runtime should not start as an abstract kernel first; it should grow from the working agent's `StepTrace`, `Evidence`, gates, handoff, effect records, and verification records.

### Capability Priority

| Priority | Capability scope | `v0.1` execution meaning |
| --- | --- | --- |
| P0 | CLI, config, `AGENTS.md` loader, session management, agent-loop / phase runner, built-in tools including minimal changed-files / diff summary, minimal MCP bridge, local skills, local commands, permission, evidence / trace, `AgentHandoff` | Must form the minimal contract-first code agent loop; if missing, `v0.1` cannot claim a runnable code agent |
| P1 | provider hardening, prompt registry, context lanes, fuller diff review / review workflow, external capability boundary hardening | May enter an early implementation slice, but must not expand into full plugins, IDE/TUI, or external tool ecosystem |
| Deferred | full `ActionGraph` scheduler, multi-agent, plugin marketplace, MCP marketplace / resource / prompt ecosystem, skill hub, command marketplace, remote, strong sandbox claims | Not part of `v0.1` acceptance; wording must clearly mark these as later evolution targets |

### TUI Plan Alignment

This document re-establishes the TUI / output decisions: `v0.1` does not introduce a formal TUI / IDE cockpit and does not include TUI in release acceptance. `v0.1` output acceptance remains headless JSON / text `AgentHandoff`.

Execution alignment:

- `--output json` / `--output text` must remain available for non-TTY, CI, redirected output, and automation.
- `--ui tui` or a standalone experimental command may only be opt-in; it must not change default `fluxcode run <task>` handoff behavior.
- TUI only consumes runtime events, `StepTrace`, permission prompt state, and final `AgentHandoff`; it must not drive permissions, sessions, or runtime mutation.
- Runtime core must not import `react`, `ink`, or `@opentui/*`, and must not introduce Bun / Zig / native build chains.
- Any later Ink PoC must use an optional / lazy / experimental boundary; if the selected Ink path requires Node `>=22`, it must have a Node gate.
- `OpenTUI` remains only a `v0.4+` adapter evaluation gate; it is not a required `v0.4` or `v0.1` deliverable.

### Contract-first Immediate Slice

The immediate implementation slice must lock contracts before provider / tool coding:

1. Lock the `v0.1` code-agent contract: CLI / config, `TaskRunState`, session lifecycle, `AGENTS.md` snapshot/hash, `AgentHandoff`, provider contract, minimal MCP / local skill / local command contracts, shell allowlist / declared-command discovery, blocked / ask / deny semantics, and test command convention.
   - The canonical `TaskRunState.status` set is `queued` / `running` / `waiting_permission` / `blocked` / `failed` / `completed`; legacy `denied` is compatibility-only and maps to `blocked` in headless envelopes and the `graph-ready` wrapper.
   - `PendingInput` / `ResumeInput` are the fixed headless run / resume contracts: permission resume uses `permissionId`, question resume uses `questionId`, and the same ids are shared by `TaskRunState.resume`, the event log, and `AgentHandoff.blockers` / `requiredDecisions`.
   - The minimum `--output json` headless envelope is `runId`, `status`, `pendingInput?`, and `handoff?`; TUI or legacy loop output must not redefine this contract.
2. Provider / config gate: real providers must be explicitly configured and fail fast; deterministic fake / mock providers remain for tests.
3. Artifact schemas: `TaskSpec`, `ContextPack`, `ChangePlan`, `PatchSummary`, `VerificationResult`, `PermissionDecision`, `StepTrace`, and `AgentHandoff`.
4. Tools: built-in read/search/edit/write/shell/manifest/minimal diff summary; P0 `git_diff` is only for changed files / diff summary, not `v0.1` git write automation; fuller diff review / review workflow stays P1.
5. Minimal MCP / skill / command: MCP only lists/calls tools from config-defined servers and is disabled by default or explicitly enabled; skills only load local instruction / workflow / command bundles; command specs only route through `TaskSpec` / phase / session.
6. Phase runner: wrap the existing ReAct loop with `Intake -> Understand -> Plan -> Edit -> Verify -> Handoff`, and keep the main path as `CLI / local command / local skill / minimal MCP bridge / built-in tools -> TaskSpec -> Session / TaskRunState -> ContextPack -> AgentLoop / PhaseRunner -> PermissionDecision -> Evidence / StepTrace -> AgentHandoff`.
7. Fixture tests: cover read-plan-edit-verify-handoff, permission ask/deny, verification failure, context overflow, ambiguous scaffold / dependency blocking, session resume, AGENTS loading, MCP disabled / enabled, and skill / command routing with fake / mock models.

## 1. Overall Choice

`v0.1` follows a small-dependency, strong-boundary, testable implementation strategy:

- Do not add LangChain, Vercel AI SDK, Commander, Zod, tree-sitter, simple-git, or execa as runtime dependencies.
- Use Node.js >= 20 standard capabilities: `fetch`, `fs/promises`, `child_process`, `AbortController`, `crypto`.
- Implement minimal provider, schema guards, edit tool, shell policy, prompt registry, and context compaction in-house first.
- Introduce dependencies later only when the in-house `v0.1` implementation cannot support safety or maintainability.

Reason: current `package.json` only has TypeScript / Vitest dev dependencies. `v0.1` should first make the local agent loop work. Large agent frameworks would expand the debug surface and weaken Fluxcode's own runtime boundaries.

## 3. Phased Implementation Plan

### Phase 0: Contract Lock and Current Capability Baseline

Goal: lock the `v0.1` code-agent contract before changing behavior, then confirm what can be reused. Provider and mutating tool work must not begin until this contract is accepted.

Tasks:

- Fix names and semantics for `TaskRunState`, `AgentHandoff`, provider contract, and phase artifact schemas.
- Fix contracts for session lifecycle, `AGENTS.md` snapshot/hash, minimal MCP bridge, local skill loader, and local command specs.
- Fix shell allowlist / declared-command discovery, blocked / ask / deny semantics, and test command convention.
- Review `src/core/agent-loop.ts` tool call handling.
- Review `src/tools/builtin.ts` read / search / write / shell behavior.
- Review gaps in `src/config/types.ts`, `src/config/defaults.ts`, and `fluxcode.config.example.jsonc`.
- Establish tests as current baseline.

Acceptance:

- The contract checklist is confirmed in this document and the engineering baseline.
- Existing tests pass.
- Every later change has an owning file.

### Phase 1: Provider and Config

Goal: `fluxcode run` can use a real provider instead of fake default.

Tasks:

- Add `src/model/openai-compatible.ts`.
- Create provider from `config.models.default` in `createAgentLoop`.
- Extend config types with `runtime`, `prompts`, `agents`, `context`, `commands`, `skills`, `mcp`, `tools.shell.allowCommands`.
- Resolve `${ENV_NAME}` placeholders.
- Run `provider_gate` and `config_gate` before starting.

No new dependency:

- Use Node `fetch` for `/chat/completions` or OpenAI-compatible endpoint.
- Hand-write request / response mapping.

Acceptance:

- Missing API key fails fast and names the env var.
- Fake provider tests still run.
- OpenAI-compatible request mapping has unit tests.

### Phase 2: PhaseRunner and Artifacts

Goal: close existing ReAct loop with phase artifacts.

Tasks:

- Add `src/core/phases.ts`: `AgentPhase`, `PhaseContract`, default contracts.
- Add `src/core/run-state.ts`: `TaskRunState`, artifact apply, handoff builder.
- Add or extend `TaskRunStore`: create / list / show / resume, status transitions, context snapshot.
- Introduce `runPhase` in `AgentLoop`, reusing current `handleToolCall` logic.
- Parse JSON artifact from model message on phase completion.
- Allow one repair turn when schema validation fails.

No new dependency:

- Use hand-written type guards for `TaskSpec`, `ContextPack`, `ChangePlan`, `PatchSummary`, `VerificationResult`, `AgentHandoff`.

Acceptance:

- Fake model happy path runs `Intake -> Understand -> Plan -> Edit -> Verify -> Handoff`.
- Invalid artifact enters repair; repair failure blocks.

Implementation slice status (2026-06-07): the Step 3 scope has landed minimum schemas / type guards for `TaskRunState`, `TaskSpec`, `ContextPack`, `ChangePlan`, `PatchSummary`, `VerificationResult`, `StepTrace`, and `AgentHandoff`, plus the phase-gated runner, artifact repair, pending permission / question resume status transitions, and session / event / evidence binding. Step 2b then connected the CLI headless contract to `run|resume|show|list`, `--output json|text`, `resume --input '<ResumeInput JSON>'`, the canonical envelope, and status / exit-code mapping. P0 `edit_file` / manifest / diff tools, MCP / skill / command routing, and the release coverage gate remain later Step 4-6 work; this slice does not make them complete.

### Phase 3: Tools and Gates

Goal: support real code changes and verification with P0 gates.

Tasks:

- Add `edit_file`.
- Add `read_project_manifest`.
- Add lightweight read-only `git_diff` for changed files / diff summary.
- Add minimal MCP bridge: config-defined servers, list/call tools, disabled-by-default / explicit enabled, unified permission / evidence / trace / session.
- Tighten `write_file`: overwriting existing files requires read-before-write or explicit create / overwrite intent.
- Tighten `shell_exec`: only allow allowlist, manifest scripts, or user-confirmed commands.
- Add path boundary, deny globs, stale write, edit match gates.

No new dependency:

- `edit_file` uses exact unique string matching.
- File hash uses Node `crypto`.
- Shell safety uses allowlist first; no tree-sitter shell AST.

Acceptance:

- Direct edit without prior read is rejected.
- Multiple `oldText` matches are rejected.
- `.env`, `.git`, `node_modules` paths are blocked.
- `npm install`, `rm -rf`, `git push` default to blocked / ask.

### Phase 4: Prompt and Context

Goal: prompts are testable and versioned; context does not depend on full transcript.

Tasks:

- Add `src/prompts/system.ts`.
- Add `src/prompts/phases/*.ts`.
- Add `src/context/build-context.ts`.
- Add `AGENTS.md` loader and write snapshot/hash plus pinned constraints into context snapshot.
- Add local skill loader: only load local instruction / workflow / command bundles, with no direct side effects.
- Add local command specs: command -> `TaskSpec` / phase event / session.
- Build prompt from Task lane / Artifact lane / Evidence lane / Recent loop lane.
- Compress tool output and old steps when over budget.

No new dependency:

- Hand-write byte budget and truncation.
- Do not add tokenizer in `v0.1`; use conservative byte threshold.

Acceptance:

- Context overflow preserves acceptance, nonGoals, blockers, changed files, verification failures.
- Prompt id / version is written into `StepTrace`.

### Phase 5: Handoff, Recovery, Integration Tests

Goal: runnable CLI experience and integration test loop.

Tasks:

- CLI `run` outputs `AgentHandoff`.
- `EventLog` adds phase / step events.
- `TaskRunStore` supports resume.
- Session resume covers `waiting_permission`, `blocked`, `failed`, and `completed` semantics.
- Add temporary repository fixtures.
- Add snake game fixture integration test.

Acceptance:

- `fluxcode run "implement a snake game"` in an existing web app fixture produces code changes and verification results.
- Interrupted tool call resume does not leave dangling state.
- Failed verification is not reported as success.

## 4. Dependency Review

### Dependencies Explicitly Not Added

| Dependency category | Reason |
| --- | --- |
| LangChain / Vercel AI SDK | Too broad; hides tool call / provider failure details |
| Commander | CLI args are simple enough |
| Zod / Ajv | Few schemas in `v0.1`; hand-written guards are clearer |
| execa | Node `child_process` is enough; current implementation already uses it |
| tree-sitter shell parser | `v0.1` does not run arbitrary shell; only allowlist / manifest scripts |
| simple-git | No commit / push / branch automation in `v0.1` |
| diff / patch package | Strict old/new `edit_file` is enough; complex patch later |
| tokenizer | `v0.1` uses conservative byte budget; tokenizer can be provider-specific later |
| `react` / `ink` / `@opentui/*` | `v0.1` does not deliver a formal TUI; UI dependencies must not enter runtime core or the release-critical path |

### Dependencies to Reconsider Later

| Dependency category | Trigger |
| --- | --- |
| tokenizer | Provider context budget errors are frequent |
| shell parser | Need broader shell support beyond allowlist |
| patch / diff library | Need multi-file hunk patch and better diff render |
| LSP client | Need diagnostics as verification gate |
| SQLite | JSON session / evidence recovery becomes too slow |
| Ink experimental package | Evaluate only after `AgentHandoff`, runtime events, and `TuiViewModel` boundaries stabilize; if the selected path requires Node `>=22`, add a Node gate |

## 5. Technical Review

### Strengths

- Reuses existing code; no rewrite.
- Keeps ReAct usability while adding artifact boundaries.
- Avoids large frameworks, improving debuggability for provider, tool, permission, and context failures.
- Every P0 gate can be covered by unit or integration tests.
- Evolves naturally toward `ActionNode` / `ActionGraph`.

### Main Risks

| Risk | Impact | Mitigation |
| --- | --- | --- |
| Model outputs unstable JSON artifacts | Phase cannot complete | Prompt schema + one repair turn + blocked handoff |
| OpenAI-compatible provider differences | Tool call mapping fails | Adapter unit tests + provider capability flags |
| Shell allowlist too conservative | Some projects cannot verify | Ask user and record skipped / blocked verification |
| No tokenizer | Context budget imprecise | Conservative byte budget and real provider smoke tuning |
| Strict `edit_file` failures | Lower edit success | Reread file and ask for more context; no fuzzy default |
| No OS sandbox | Safety boundary limited | Do not claim sandbox; rely on permission/path/shell gates |

### Review Conclusion

The plan can implement a runnable `v0.1`, with three explicit boundaries:

- `v0.1` is a safety-constrained local code agent, not an unbounded autonomous engineer.
- `v0.1` shell is intentionally conservative; verification commands must come from allowlist, manifest, or user confirmation.
- `v0.1` delivers a minimal MCP bridge, but does not claim a full MCP platform, marketplace, resource / prompt ecosystem, skill hub, command marketplace, full sandbox, graph runtime, IDE, or multi-agent capability.

Within those boundaries, proceed to implementation.

### Real Provider Smoke

Real provider smoke is not part of default CI. Example manual command:

```bash
FLUXCODE_MODEL_API_KEY=... fluxcode run "implement a snake game in this fixture and run tests" --config fluxcode.config.jsonc
# Or, after building the CLI, run the minimal smoke hook:
FLUXCODE_MODEL_API_KEY=... npm run smoke:provider
```

Pass criteria:

- Model produces tool calls.
- Real files are changed.
- Declared verification command runs.
- `AgentHandoff` is emitted.
- Happy path completes without human intervention; dependency install or scaffold needs ask / block.
