# v0.1 Engineering Baseline

## Status

This document is the milestone engineering baseline target for Lattecode `v0.1`, not a module design under `design/`. It defines the concrete details required to really run tasks such as `lattecode run "implement a snake game"`: AI providers, configuration, `AGENTS.md` loader, session management, tools, minimal MCP bridge, local skills, local commands, prompt management, and context compaction.

Chinese counterpart: [`docs/zh-CN/milestones/targets/v0.1-engineering-baseline.md`](../../../zh-CN/milestones/targets/v0.1-engineering-baseline.md).

## 1. Goal

The engineering goal for `v0.1` is: in a local repository with an existing application foundation, Lattecode can call a real model through CLI, read context, modify source code, run declared verification commands, and produce reviewable handoff.

This requires more than an abstract loop. `v0.1` needs:

- A real usable model provider adapter.
- A stable internal `ModelClient` protocol to hide provider differences.
- An explainable, overridable, no-secrets JSONC config file.
- A minimal `AGENTS.md` loader that puts repository constraints into context with snapshot/hash.
- Local session management with create / list / show / resume.
- A minimal tool set sufficient for small coding tasks.
- A minimal MCP bridge that is disabled by default or explicitly enabled.
- A local skill loader that only loads local instruction / workflow / command bundles.
- Built-in / local command specs that route into `TaskSpec`.
- Versioned and testable phase prompts.
- Context budget / compaction that does not depend on full transcript.

## Contract Lock Before Implementation

`v0.1` implementation must lock the code-agent contract before provider adapter, tool, or phase runner coding begins. This contract is the implementation acceptance basis; it does not mean the current `src/` already has these capabilities.

The contract must first define:

- `TaskRunState`: run id, task input, phase status, artifact refs, verification status, blocked reason, and resume marker.
- `PendingInput` / `ResumeInput`: `waiting_permission` uses permission input with `permissionId`; `blocked` uses question input with `questionId`; CLI resume, `TaskRunState.resume`, the event log, and `AgentHandoff` must reuse the same ids.
- Session contract: stable session id, create / list / show / resume, fixed cwd / repo root, context snapshot, status transitions, and resume semantics.
- `AgentHandoff`: final summary, changed files, verification, risks, blockers, required user decisions, and trace / evidence refs.
- `AGENTS.md` contract: load scope, snapshot/hash, conflict handling, missing / unreadable semantics, and where it enters `ContextPack`.
- Provider contract: `ModelClient` request / response, tool-call turn, tool-result turn, provider error, missing-credential fail-fast behavior, and fake / mock provider test path.
- MCP contract: config-defined servers, list/call tools, disabled-by-default / explicit enabled, unified permission / evidence / trace / session binding, and no permission bypass.
- Skill contract: local skill loader, instruction / workflow / command bundle, context / prompt registry injection, and no direct side effects.
- Command contract: built-in / local command specs, command -> `TaskSpec` / phase event / session, and no bypass of agent-loop / permission / session.
- Shell contract: allowlist, declared-command discovery, timeout, output cap, blocked / ask / deny records, and test command convention.
- Tool contract: read-only / mutating classification, path boundary, read-before-write, stale write, edit match, and permission decision.
- Artifact contract: minimal fields and schema guards for `TaskSpec`, `ContextPack`, `ChangePlan`, `PatchSummary`, `VerificationResult`, and `AgentHandoff`.
- Headless output envelope: `runId`, `status`, `pendingInput?`, and `handoff?` are the minimum machine-readable `--output json` fields; legacy `denied` may only survive as a compatibility status mapped to canonical `blocked`.

Contract lock acceptance is review-only: confirm goals, non-goals, schemas, failure states, and test conventions. Real provider or mutating tool implementation should not start before this is accepted, otherwise unreviewed interfaces may harden into code.

## Output and UI Boundary

This document re-establishes the `v0.1` output / TUI decisions. The `v0.1` engineering baseline does not deliver a formal TUI / IDE cockpit and does not include TUI in release acceptance; the release-critical path remains headless JSON / text `AgentHandoff`.

CLI output boundary:

- `--output json` and `--output text` must remain available for non-TTY, CI, redirected output, automation, and crash fallback.
- `--ui tui` or a standalone experimental command may only be explicit opt-in; default `lattecode run <task>` must not depend on TUI.
- The `AgentHandoff` schema does not change because UI exists; UI may only display handoff, runtime events, `StepTrace`, and permission prompt state.
- TUI must not drive permissions, sessions, or runtime mutation, and must not bypass schema, permission, evidence, trace, or handoff.
- Runtime core must not import `react`, `ink`, or `@opentui/*`; the main runtime must not introduce Bun / Zig / native build chains.

If renderers are introduced later, the boundary must be:

```text
runtime event stream
  -> stable TuiViewModel
  -> InkRenderer | OpenTuiRenderer | PlainTextRenderer
```

`PlainTextRenderer` is the default path for non-TTY, CI, snapshots, and crash fallback. Ink may only be a later optional / lazy / experimental PoC; if the selected Ink path requires Node `>=22`, it must have a Node gate. `OpenTUI` is only a `v0.4+` adapter evaluation gate; only if `ActionGraph` becomes a real UX surface in `v0.5+` should it be reconsidered as a cockpit hardening candidate.

## 2. AI Provider Plan

### 2.1 Internal Protocol First

Lattecode internally depends only on `ModelClient`. The core loop must not directly depend on OpenAI, Anthropic, Claude Code, MCP, or any vendor protocol.

```ts
type ModelTurn =
  | { type: "message"; content: string }
  | { type: "tool_calls"; content?: string; toolCalls: ToolCall[] };

interface ModelClient {
  generate(request: ModelRequest): Promise<ModelTurn>;
}
```

Provider adapters translate external protocols into this canonical form:

| External difference | Internal normalization |
| --- | --- |
| OpenAI tool calls / Anthropic tool_use naming | Normalize to `ToolCall[]` |
| Streaming / non-streaming | `v0.1` supports non-streaming first; streaming only affects UI later |
| system / developer / user message differences | Normalize to `ModelMessage[]`, mapped inside adapter |
| Token parameter naming | Normalize to `maxOutputTokens`, `temperature` |
| JSON mode / tool choice support | Do not depend on strong JSON mode in `v0.1`; use prompt + schema repair fallback |

### 2.2 `v0.1` Provider Priority

| Priority | Provider | Use | Notes |
| --- | --- | --- | --- |
| P0 | `fake` | Unit and integration tests | Already exists and must remain |
| P0 | `openai-compatible` | First real model adapter | Covers OpenAI, Azure OpenAI, OpenAI-compatible local models or gateways |
| P1 | `anthropic-compatible` | Claude / Anthropic Messages API | Closer to Claude Code tool_use semantics |
| P2 | `custom-command` | Local command or internal enterprise model proxy | Implement only when there is concrete demand |

`v0.1` should not abstract through LangChain or Vercel AI SDK. Keep adapters small and transparent so tool calls and permission issues remain debuggable.

### 2.3 Provider Failure Semantics

| Scenario | Handling |
| --- | --- |
| Missing API key | Fail before run and report missing env name |
| 429 / rate limit | Record provider error and optionally retry with limited config |
| Tool call JSON parse failure | Enter one schema repair turn; if still failing, block current phase |
| Model does not support tools | Fail before start or phase start; do not degrade to text-only execution |
| Output too long | Store truncated summary and truncation marker; do not feed long output back unbounded |

## 3. Config Design

### 3.1 Config File Role

The config file is runtime policy, not secrets storage. Default discovery paths:

```text
~/.lattecode/lattecode.jsonc
~/.lattecode/lattecode.json
.lattecode/lattecode.jsonc
.lattecode/lattecode.json
```

Rules:

- Within the same level, read `lattecode.jsonc` first and fall back to `lattecode.json` when JSONC is absent.
- When global and project configs both exist, read both and deep-merge by key.
- Merge order: default config -> global config -> project config -> CLI flags; project config overrides global config.
- API keys are referenced only through environment variables such as `apiKeyEnv`.
- Default config must run `fake` provider tests.
- Real provider must be explicitly selected as default; global config must not store secrets directly.

## 4. Minimal Tools

`v0.1` tools should be sufficient for small coding tasks and have clear safety boundaries.

| Tool | Priority | Mutating | Use | Current state |
| --- | --- | --- | --- | --- |
| `list_directory` | P0 | no | Inspect repository structure | Exists |
| `read_file` | P0 | no | Read source, tests, config | Exists |
| `search` | P0 | no | Search symbols, text, test entries | Exists |
| `edit_file` | P0 | yes | Local replace / insert edits | Implemented for P0: exact replace / unique anchor insert through read-before-write, stale-write, and edit-match gates |
| `write_file` | P0 | yes | Create new files or overwrite small files | Constrained for P0: new files require explicit `createIntent=true`; overwrites require same-run read with unchanged hash |
| `shell_exec` | P0 | yes | Run declared verification commands | Constrained for P0: allows only `tools.shell.allowCommands`, `package.json` scripts, or permission ask/deny paths |
| `read_project_manifest` | P0 | no | Summarize package / tsconfig / test config | Implemented as P0 summary: returns config files and package scripts / declared commands |
| `git_diff` | P0 | no | Produce changed files / diff summary for `AgentHandoff` and safety review | Implemented as P0 summary-only; no git write automation or full review workflow |
| `diagnostics` | P1 | no | LSP / TypeScript diagnostics | Later |

The minimal MCP bridge is not a replacement for built-in tools. It only maps config-defined server tools into the Lattecode tool contract and routes them through the same permission, evidence, trace, and session pipeline; it is disabled by default or explicitly enabled. `v0.1` does not deliver a marketplace, resource / prompt ecosystem, or server-management UI.

### 4.1 Why `edit_file` Is Required

Only having `write_file` pushes the model toward whole-file rewrites. `edit_file` should support scoped edits:

```ts
type EditFileInput =
  | { path: string; mode: "replace"; oldText: string; newText: string; replaceAll?: boolean }
  | { path: string; mode: "insert_after" | "insert_before"; anchor: string; text: string };
```

Constraints:

- `oldText` must match exactly once unless `replaceAll=true`.
- Record file hash or mtime before editing for stale-write protection.
- Return changed bytes, matched range, and summary.

### 4.2 Shell Command Policy

`shell_exec` must not be arbitrary shell. `v0.1` only allows:

- Commands explicitly listed in `tools.shell.allowCommands`.
- Scripts declared in project manifests, such as `npm test` or `npm run build`.
- Commands explicitly confirmed by the user in the current turn.

Default blocks:

- install: `npm install`, `pnpm add`, `pip install`.
- delete: `rm -rf`, bulk deletion.
- network: curl, wget, remote scripts.
- git write: commit, push, reset, checkout, rebase.

## 5. Prompt Management

Prompts should not be scattered as string literals. `v0.1` needs a lightweight prompt registry.

Recommended structure:

```text
src/prompts/
  system.ts
  phases/
    intake.ts
    understand.ts
    plan.ts
    edit.ts
    verify.ts
    handoff.ts
```

Each prompt defines:

```ts
type PromptTemplate = {
  id: string;
  version: string;
  phase: AgentPhase;
  render(input: PromptRenderInput): ModelMessage[];
  expectedOutput: string;
};
```

Prompt rules:

- System prompt describes identity, tool boundaries, safety constraints, and artifact output rules.
- Phase prompt describes current phase goal, allowed tools, output schema, and failure handling.
- Do not concatenate large transcript history into prompts; pass only `TaskSpec`, phase artifacts, recent steps, and necessary evidence summaries.
- Write prompt id and version into `StepTrace` for reproducibility.
- Custom prompts may be supported later, but `v0.1` should not allow project prompts to override safety rules arbitrarily.

## 6. Context Compaction

`v0.1` does not need a complex memory system, but it must prevent unbounded transcript growth.

### 6.1 Context Lanes

Each model call uses four lanes:

| Lane | Content | Compressible |
| --- | --- | --- |
| Task lane | `TaskSpec.objective`, acceptance, constraints, nonGoals | Never drop |
| Artifact lane | `ContextPack`, `ChangePlan`, `PatchSummary`, `VerificationResult` | Summarize but keep refs |
| Evidence lane | Tool summaries, file refs, command output summaries | Compressible |
| Recent loop lane | Recent N ReAct observations in current phase | Sliding window |

### 6.2 Compaction Strategy

When prompt exceeds `context.maxPromptBytes`, apply in order:

1. Truncate long tool outputs, keeping summary, references, and truncation marker.
2. Compress old `StepTrace` records into phase summaries.
3. Preserve changed files, verification failures, user constraints, and open blockers.
4. Keep only paths, reasons, and necessary snippets for previously read files.
5. If still over budget, block current phase and ask to narrow scope.

Never compact away:

- User acceptance criteria.
- User explicit non-goals.
- Permission denials or pending confirmations.
- Changed file list.
- Verification failure summary.

## 7. Current Code Gaps

| Gap | Impact | `v0.1` handling |
| --- | --- | --- |
| `openai-compatible` adapter not implemented | CLI can only fake | Implement real provider adapter |
| `config-schema` validates only top level | Config errors are found late | Add runtime / prompts / context / shell allowlist validation |
| `edit_file` P0 is now present | Real edits trend toward whole-file overwrite | Keep scoped edits behind read-before-write, stale-write, and edit-match gates |
| `shell_exec` P0 is now constrained | Command risk is high | Keep declared command discovery, allowlist, and dangerous-command deny/ask behavior |
| Lightweight read-only `git_diff` P0 is now present | Handoff lacks changed files / diff summary | Keep P0 summary-only `git_diff`; fuller diff review / review workflow stays P1 |
| Missing explicit `v0.1` code-agent contract | Provider, tools, and phase runner may define divergent interfaces | Lock contract before adapter / tool / runner implementation |
| Session contract too narrow | Resume and permission states are hard to recover | Add create / list / show / resume, status transitions, and context snapshot |
| Missing `AGENTS.md` loader contract | Repository constraints may become untracked prompt text | Add snapshot/hash and context binding |
| Missing minimal MCP bridge | External tools cannot enter the unified permission and evidence pipeline | Add disabled-by-default / explicitly-enabled list/call tools bridge |
| Missing local skill loader | Local workflows cannot be reused as controlled context capabilities | Add local-only skill loader with no direct side effects |
| Missing local command specs | Commands may bypass the agent loop | Add command -> `TaskSpec` / phase event / session routing |
| Prompt hard-coded in `agent-loop.ts` | Hard to test and version | Add prompt registry |
| Context depends on transcript | Long tasks are uncontrolled | Add context builder / compactor |
| CLI output is still loop result | Missing handoff | Output `AgentHandoff` and artifact paths |
| Missing output / UI boundary | TUI may accidentally enter the `v0.1` release-critical path | Keep `--output json` / `--output text`; TUI is opt-in only and does not enter runtime core |

### 7.1 Step 5 Implementation Alignment Status

The current `src/` now includes the minimum Step 5 implementation slice for `v0.1`: `AGENTS.md` is loaded within repo root / cwd boundaries and enters `ContextSnapshot` as snapshot/hash/summary; local skills inject only instructions / workflows / command specs into prompt/context; local commands are converted into `TaskSpec`, recorded as session events, and then continue through the phase runner; the minimal MCP bridge exposes only explicitly enabled server tools and registers them as Lattecode `ToolRegistry` tools that pass through permission, evidence, trace, and session; phase prompts render through a lightweight prompt registry, and the context builder / compactor preserves task, acceptance, constraints, changed files, and verification lanes before model calls.

This is only the Step 5 adapter / prompt / context wiring status. It does not claim that the Step 6 final release path, coverage gate, real-provider smoke path, or complete handoff/recovery acceptance is finished.

### 7.2 Step 6 Implementation Alignment Status

The current `src/` now includes the Step 6 release-path wiring: `AgentHandoff` is finalized before output with `changedFiles`, verification, risks, trace refs, and evidence refs; `recovery_gate` repairs resumable blocked pending input and explicitly converges to a failed handoff when failed / completed handoff data is missing or pending tool state is dangling; CLI `run|resume|show|list` continues to emit the headless envelope and returns the frozen status / exit-code mapping; the `graph-ready` wrapper only consumes the headless contract and does not define the runtime main path.

Tests now include a fake-model release-path fixture, resume negative/fallback fixtures, coverage edge fixtures, and the manual real-provider smoke hook `npm run smoke:provider`. Regular acceptance remains deterministic fake-model integration; real-provider smoke requires `npm run build` plus `LATTECODE_MODEL_API_KEY`, with optional `LATTECODE_MODEL_BASE_URL` / `LATTECODE_MODEL_NAME`.

## 8. `v0.1` Implementation Order

1. Lock the `v0.1` code-agent contract: `TaskRunState`, session lifecycle, `AGENTS.md` snapshot/hash, `AgentHandoff`, provider contract, MCP / skill / command contracts, shell allowlist / declared-command discovery, blocked / ask / deny semantics, and test command convention.
2. Implement provider / config gates and add the `openai-compatible` `ModelClient` adapter; real providers must be explicitly configured and fail fast.
3. Extend config: `runtime`, `prompts`, `agents`, `context`, `commands`, `skills`, `mcp`, `tools.shell.allowCommands`.
4. Add artifact schema guards: `TaskSpec`, `ContextPack`, `ChangePlan`, `PatchSummary`, `VerificationResult`, and `AgentHandoff`.
5. Add session management: create / list / show / resume, status transitions, context snapshot, trace / evidence binding.
6. Add the `AGENTS.md` loader and write snapshot/hash into session context.
7. Add `edit_file`, `read_project_manifest`, lightweight read-only `git_diff`, and tighten `shell_exec`.
8. Add minimal MCP bridge, local skill loader, and local command specs, all routed through `TaskSpec -> Session -> PhaseRunner`.
9. Add prompt registry, phase prompts, and context builder / compactor.
10. Add `PhaseRunner` to close the existing loop into `Intake -> Understand -> Plan -> Edit -> Verify -> Handoff`.
11. Make CLI `run` output `AgentHandoff`, not only final natural-language text.
12. Lock output / UI boundary: non-TTY and CI use JSON / text or `PlainTextRenderer` fallback; experimental TUI does not change default handoff.
13. Use `FakeModelClient` / deterministic mock provider for happy path, provider error, permission ask / deny, verification fail, context overflow, ambiguous scaffold / dependency blocking, session resume, AGENTS loading, MCP disabled / enabled, and skill / command routing tests.

## 9. Acceptance

- After configuring a real provider, `lattecode run "implement a snake game"` no longer returns the fake default message.
- In an existing Web / frontend repository, agent can create or modify source files.
- Agent can run declared test or build command and write the result into handoff.
- When framework or dependency decisions are missing, agent blocks clearly and asks for confirmation.
- Prompt, context, tools, provider, and permission decisions are traceable in event log or step trace.
- Session lifecycle, `AGENTS.md` snapshot/hash, minimal MCP bridge, local skills, and local commands all enter the same permission / evidence / trace / session pipeline.
- `--output json` / `--output text` remain available; without explicit opt-in, TUI does not affect `AgentHandoff` output or `v0.1` acceptance.
